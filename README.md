# FB Video Automation — Backend (Phase 2)

FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL. **No Facebook publishing and no Meta calls exist in this phase.**
`/health` reports `publishing_enabled: false`. Pinned versions: `requirements.txt`.

## Run with Docker
```bash
cp .env.example .env        # replace every CHANGE_ME
docker compose up --build   # runs migrations, then the API on http://localhost:8000
```
Create the storage bucket (name = `S3_BUCKET`) in the MinIO console at http://localhost:9001.
Interactive API docs: http://localhost:8000/docs · Login with `ADMIN_EMAIL` / `ADMIN_PASSWORD`.

## Run tests (no Postgres/S3 needed — uses in-memory SQLite and a fake storage)
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
```

## Migrations
```bash
alembic upgrade head
alembic revision --autogenerate -m "describe change"   # for every future model change
```

`POST /api/auth/login` · `GET /api/auth/me` · `/api/accounts` · `/api/pages` (+ `/pause`, `/resume`) · `/api/videos` (+ `/upload-url`, `/{id}/complete`) ·

## Design notes
- Passwords: bcrypt. Sessions: short-lived signed JWT (default 30 min); no public sign-up; failed-login throttle (per process).
- Meta tokens: encrypted with Fernet at rest and absent from every response schema.
- Videos: browser uploads straight to S3-compatible storage with a presigned URL; the API never stores files locally.
- New pages start paused and "needs attention"; they can only be resumed when status is `connected`. In `production` mode status can't be edited by hand (it will come from Meta checks in Phase 3).
- Analytics: `null` = unavailable from Meta, `0` = reported zero.
- The baseline migration uses `create_all`; all later changes should be autogenerated migrations.

## Media: videos and images
- `/api/media` replaces `/api/videos`. Accepted: `.mp4/.mov/.m4v` videos (max `MAX_UPLOAD_BYTES`, default 2 GB) and `.jpg/.jpeg/.png` images (max `MAX_IMAGE_BYTES`, default 10 MB). Type is decided by the server from extension + content type. Confirm Meta's current photo limits before Phase 4.
- Each page has a daily plan: `daily_video_limit` + `daily_image_limit` (0–50 each, total 1–50). `daily_limit` and `media_mode` are derived from them. Queue creation rejects a job when that page's allowance for that media type is used up for that calendar day **in the page's timezone**.
- The automatic choosing of which item to post, repeat-avoidance and "same item on too many pages" limits are part of the Phase 4 publishing engine.
- Existing databases: run `alembic upgrade head` (migrations 0002/0003 add the new columns and convert old settings; it does nothing on a fresh database).
